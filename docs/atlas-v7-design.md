# ARIA Atlas V7 — Project Knowledge Graph and Artifact Vault

## Purpose

Atlas V5 added durable execution and V6 added delegated operator teams. V7 gives those systems a durable project memory that is more structured than a chronological event list. It records what the project is made of, why decisions were made, which evidence supports them, which artifacts were produced, what is stale or conflicting, and how each item traces back to its source.

V7 remains inside the existing Render bot and owner-scoped Atlas workspace. It does not claim that ARIA is conscious and it does not introduce a new provider integration. The graph is a deterministic index over project records and artifacts, not an unrestricted autonomous knowledge system.

## Architecture choice

| Approach | Tradeoffs | Cost | Setup complexity |
|---|---|---:|---:|
| Extend each Atlas workspace with a bounded graph and artifact vault | Reuses existing atomic workspace persistence, evidence, decisions, tasks, risks, executions, teams, and dashboard authentication. | Lowest; no new service | Medium |
| Add a separate graph database and document store | Stronger graph querying and scale, but introduces deployment, backup, consistency, credentials, and migration work before the product model is proven. | Higher | High |

V7 uses a bounded JSON graph inside each existing workspace. The implementation provides typed indexes and deterministic queries now, while preserving a migration path to a dedicated database only if real project volume requires it.

## Knowledge model

A workspace stores bounded `knowledgeNodes`, `knowledgeEdges`, and `artifacts`. Existing Atlas records remain the source of truth for tasks, decisions, evidence, risks, missions, executions, operator teams, and retrospectives. V7 adds graph projections and explicit artifact references rather than copying whole records into a second hidden database.

| Node type | Meaning | Typical source |
|---|---|---|
| `requirement` | A desired outcome, constraint, acceptance criterion, or non-goal. | Project contract, task, operator packet |
| `decision` | A recorded choice with rationale and alternatives. | Atlas decision record |
| `risk` | An uncertainty, blocker, failure, or mitigation concern. | Risk register, Sentinel, team recovery |
| `task` | A unit of work and its lifecycle state. | Atlas task |
| `evidence` | A fact, test result, source, signal, or mission outcome. | Atlas evidence and Sentinel |
| `artifact` | A produced file, URL, report, screenshot, archive, or generated output. | Build, dashboard, mission, operator team |
| `execution` | A V5 run or V6 team packet that produced or consumed project context. | Execution Core, Operator Teams |
| `external_reference` | A link or named external reference that is intentionally recorded without provider synchronization. | WhatsApp note, URL, future GitHub/Render integration |

Each node has a stable ID, type, title, summary, status, source record ID, artifact IDs, confidence, sensitivity, freshness metadata, and timestamps. Node summaries are bounded and sanitized. Secrets, tokens, raw provider payloads, and arbitrary instructions are not persisted as graph content.

## Typed edges

Edges express relationships without embedding hidden behavior. The initial edge types are `supports`, `contradicts`, `depends_on`, `produced_by`, `derived_from`, `satisfies`, `blocks`, `supersedes`, `references`, and `related_to`. Each edge stores source and target node IDs, a short rationale, provenance record IDs, confidence, and creation/update timestamps.

Edges are owner-scoped and validated: both endpoints must exist, self-links are rejected, duplicate `(source, type, target)` links are idempotent, and a node cannot be deleted while a live edge depends on it. V7 does not infer an edge merely because two titles contain similar words; every edge is explicit or generated by a deterministic projection rule.

## Artifact Vault

The artifact vault stores metadata and provenance, not arbitrary executable content. An artifact includes an ID, kind, title, safe HTTP URL or local relative path, content type, size, checksum when available, source role, source mission/team/execution IDs, related node IDs, lifecycle status, sensitivity, and timestamps.

| Artifact rule | V7 behavior |
|---|---|
| URL safety | Only `http` and `https` URLs are accepted; credentials in URLs are rejected. |
| Local paths | Paths are relative to the project data area and normalized against traversal. |
| Provenance | Every artifact must identify its source kind and source record when available. |
| Deduplication | A stable checksum or canonical URL prevents duplicate vault records. |
| Freshness | Artifacts may be marked `fresh`, `stale`, `unknown`, or `superseded`. |
| Limits | Artifact metadata, titles, summaries, paths, and URLs are bounded per workspace. |

V7 does not upload files, execute artifacts, or publish them externally. It makes produced outputs traceable. Existing secure file and media systems remain responsible for actual access control and delivery.

## Projection and consistency

When a workspace is read, V7 can deterministically project core Atlas records into graph nodes: the project contract becomes a requirement, tasks become task nodes, decisions become decision nodes, open risks become risk nodes, evidence becomes evidence nodes, and V5/V6 results become execution or artifact-related nodes. Explicit user-created nodes and edges remain durable. Projection IDs are stable so repeated refreshes do not duplicate them.

A `knowledgeRevision` and `lastProjectedAt` value identify the current graph projection. When an underlying record changes, the next projection updates the corresponding node’s freshness and source timestamp. The graph is a view with provenance, not a second conflicting task or decision store.

## Freshness and conflict detection

V7 provides deterministic health checks rather than pretending to resolve ambiguity automatically. It reports stale nodes when their source record is older than the requested threshold, orphaned edges when an endpoint is missing, unsupported links when edge types are invalid, and conflicts when a node has both `supports` and `contradicts` relationships to the same target or when two active decisions supersede each other without an explicit edge.

Conflict reports are advisory evidence. ARIA can propose a resolution or ask the owner to choose; V7 never silently rewrites a decision, closes a risk, deletes an artifact, or changes a task because of a graph finding.

## Natural-language surface

The owner can say:

- “Show the project knowledge graph.”
- “What supports this requirement?”
- “What is blocking this project?”
- “Show stale project knowledge.”
- “Show conflicts in the project.”
- “Trace this artifact.”
- “Link this evidence to the release decision.”
- “Record this as a project requirement.”
- “Add this artifact to the project vault.”
- “What changed in the project knowledge?”

These actions are owner-scoped and no prefix is required. Query results include provenance IDs and source timestamps so ARIA can explain where a conclusion came from.

## Dashboard cockpit

The Atlas dashboard adds a Knowledge Graph panel with node counts, recent artifacts, stale/conflict warnings, and a compact relationship explorer. It exposes authenticated, CSRF-protected actions for projecting the graph, adding a node, linking two existing nodes, and refreshing the artifact view. It does not expose arbitrary file execution, upload, deletion, commit, deployment, or external posting.

## Deferred integrations

GitHub and Render linking remain deferred. V7 records external references and supports future provenance inputs, but no provider-side synchronization is enabled by this release.
